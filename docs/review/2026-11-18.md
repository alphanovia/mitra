# Review list for 2026-11-18

What was built overnight, and what to look at together. Increments are in
order; each one was tested, pushed to main, reviewed by a red-team agent,
and followed by a commit with the fixes. Start with "Decisions taken
alone" and "Open questions"; each increment has What to review / How to
test.

## Decisions taken alone

1. **Verdict output** prints `domain := Bool`, not `univ` as the design doc
   sketched: the type name says more. (lean-syntax.md notes the difference.)
2. **Golden files were converted by a program** (old parser + new printer),
   keeping comments. Expected results were translated by a script, so the
   values are the hand-written ones; only their spelling changed.
3. **Unicode only**: `∀ ∈ ∪ ∩ ¬ ×ˢ` have no ASCII spelling yet (open
   question in lean-syntax.md).
4. **`evidence c at 1`** with no arguments means the claim on its whole
   domain (was `c(_, _) holds`).
5. **`f args = g`** with a bare function name `g` still means `g` applied to
   the same inputs. It is not Lean-like; kept because the evaluator has it.

6. **Store layout**: one `.mitra/` folder with `model.mitra` and one
   append-only `evidence.mitra`, merged by git's `union` driver, rather than
   the `.mitra/evidence/` folder or git notes in workflow.md. Simplest that
   merges cleanly.
7. **Provenance as Lean-style attributes**: `@[source "ci", rev "3f2a"]
   evidence …`. Recorded, not used by verdicts yet (no staleness yet).
8. **`mitra add` does not read git**: `--rev` is explicit. Predictable, and
   no hidden dependency on git.

9. **Tests are declared in the model**: `test t : <judgment>` (same
   judgment syntax as evidence), not in comments next to the test code as
   workflow.md sketched. One place, checked by the parser; comment
   extraction can come later.
10. **A failed test over a set gives no evidence** (only a note): Mitra has
    no "wrong somewhere in S" yet (composition.md open question 2). A failed
    `f x = v` test gives nothing either.
11. **Test names** are the last `::` segment of the report's path, so two
    tests with the same short name in different modules collide.

12. **`mitra next` is simple**: per uncertain claim, the missing inputs and
    up to 5 evidence lines to write; no ranking across claims yet, no
    weighting by profile.

13. **mitra-ds models masses as numbered cases** (`case : Icc 0 1003`):
    Mitra has no reals or rationals, so a claim is about the cases the
    property tests draw, not about all masses. Honest but weak; rationals
    are the prerequisite dogfooding.md already lists.
14. **mitra-core does not use mitra-ds yet**: intermediate confidences are
    still rejected. The calculus is not chosen (DS + Yager is only the
    recommendation), so wiring it in is left for a decision with you.

15. **Staleness, first cut**: `--rev R` on `check`/`eval`/`next` leaves out
    evidence recorded at any other revision. Crude (every commit makes all
    earlier evidence stale, even for subjects that did not change), but
    safe. The design's per-subject content hash needs subjects linked to
    code, which Mitra doesn't have yet.

16. **A failed negative test gives no evidence** (`test t : ¬ correct (f 1)`
    failing does not mean `correct (f 1)`: the test may have failed for
    another reason). A test listed twice in one report is left out.

17. **`--rev R` counts only evidence recorded at `R`**, including leaving
    out evidence with no `rev`. The first cut kept rev-less evidence, and
    the red team showed an old manual pass could then hide a newer failure
    (the failure, at another revision, was left out). Safe but blunt:
    manual evidence must carry `--rev` to count under `--rev`.
18. **The dogfood revision is the hash of the crate's code**, not the
    commit: committing the evidence file then doesn't make it stale.

## Open questions

- ASCII alternatives for the Unicode symbols?
- `mitra next` suggests evidence on inputs that are *contradicted* (both
  correct and wrong at 1), as if nothing was known there; it should say
  "contradicted" instead. Needs the verdict to carry the contradictions.
- Should `contested evidence …` lines become Lean comments (`-- …`) so the
  whole output reads as Lean?

## Increments

### 1. Lean-inspired syntax and grammar checks (b5e63ed, 127edd3)

What to review:
- `docs/reference/language.md`: lexical rules, grammar, commands, output.
- `tests/golden/*`: read two or three converted cases (e.g. `minus/strict/03`).
- `crates/mitra-grammar/src/mitra.ll1` and `mitra.lalrpop`: the grammar in
  both forms.
- `crates/mitra-grammar/mitra/parser.mitra`: the dogfood claims.

How to test:
```sh
cargo test                       # everything, incl. LL(1), LR(1) build, fuzzer, dogfood
cargo run -p mitra-grammar --example sample -- 7   # see a generated program
cd tree-sitter-mitra && npm install && npx tree-sitter generate \
  && npx tree-sitter test && node check-golden.js
```

Red-team findings (fixed in the follow-up commit):
- Huge weights became `inf` and broke the round trip: numbers must now be
  finite.
- Error lines for unbound or doubly bound names pointed one token late.
- `-9223372036854775808` (i64::MIN) could not be written; now it can.
- `-(5)` printed as `-5`, which reads back as a literal: the fuzzer found it
  once the generator made `- ( 5 )`.
- The reference now lists the parser's checks beyond the grammar (at least
  one argument, distinct `∀` names, 64-bit integers, finite numbers) and
  says tree-sitter accepts a superset.
- Old-syntax wording in error messages and doc comments.
- The dogfood now records failures as `= false` evidence instead of
  stopping the test, and also covers the LL(1) grammar.

Red-team findings left open:
- The fuzz checks the parser against its own printer and two *recognisers*:
  a precedence bug shared by parser and printer would pass. (Hand checks
  of the main precedence cases found none.) A fix would be a second,
  independent AST builder, e.g. LALRPOP actions building the AST.
- The generator never produces invalid programs, so "the parser accepts
  more than the grammar" is only checked by hand.

### 2. Store: `mitra init/check/eval/add`, evidence provenance (bb4b79d)

What to review:
- `docs/reference/language.md`, "Running Mitra" and "evidence" (attributes).
- `crates/mitra-cli/src/store.rs`: how `add` checks before it appends.

How to test:
```sh
cargo build && cd /tmp && rm -rf demo && mkdir demo && cd demo
~/mitra/target/debug/mitra init        # adjust the path to the repo
cp ~/mitra/tests/golden/not/strict/01_no_evidence/model.mitra .mitra/
~/mitra/target/debug/mitra add 'evidence correct (not true) at 1' --source review:me --rev abc
~/mitra/target/debug/mitra eval && cat .mitra/evidence.mitra
```

Red-team findings (fixed in the follow-up commit):
- `add` accepted an output outside the subject's result type, which then
  broke `check` and `eval`: outputs are now type-checked, and `add`
  evaluates the store before and after.
- A broken store was blamed on the new evidence: the store is now checked
  first, and errors in the new text say `evidence to add: line N`.
- `--source` given twice, or both as option and attribute, is refused;
  `eval -o` refuses `.mitra` files and names starting with `-`; a `.mitra`
  file (not folder) is an error.
- Attributes and tests now have a tree-sitter corpus case.

Red-team findings left open:
- After a git merge of two branches, nothing checks the merged store: run
  `mitra check` in CI.
- `rev` is free text and never compared with anything: staleness will need
  a fixed meaning (a git commit) later.
- Duplicate or contradictory evidence is accepted silently by `add`
  (contradictions show up in verdicts, not as warnings).
- `init` is not atomic; a UTF-8 BOM is rejected.

- A failure at confidence 1 overclaims when a test is flaky.
- Report lines it does not recognise are ignored silently (documented).
- `next` suggests evidence on contradicted inputs (see open questions), and

### 5. mitra-ds, judged by Mitra from its own test runs

What to review:
- `crates/mitra-ds/src/lib.rs` (about 100 lines) and `tests/props.rs`.
- `crates/mitra-ds/.mitra/model.mitra`: the claims and `test` declarations;
  `.mitra/evidence.mitra`: evidence written by `mitra ingest`.
- `docs/design/dogfooding.md`, "What exists".

How to test:
```sh
scripts/dogfood-ds.sh            # runs the tests, ingests them, prints verdicts
cargo test -p mitra-cli mitra_ds # the committed store gives the expected verdicts
```
Without `--rev`, evidence from older code would still count: a pass
recorded before a bug would hide it. Increment 6 is the first answer.

Red-team findings on 5 and 6 (fixed in the follow-up commit):
- The script tagged evidence with HEAD even with uncommitted changes, and
  swallowed a build failure: a broken crate still showed `holds`. It now
  refuses uncommitted code, stops when the tests don't build or give no
  results, exits non-zero when a test fails, and tags with the code hash.
- `--rev` could make a claim hold wrongly (decision 17).
- The tests checked less than the claims say: now general masses (belief
  on both sides) on odd cases, all three parts compared, commutativity
  checked on the extremes too.
- `dempster`/`yager` accepted NaN or non-normalised masses: now `None`.
  Dempster's ε cutoff near total conflict is documented.
- `--rev ''`, `--rev --rev` were accepted: one check for all commands.

Red-team findings left open:
- Yager's rule is not associative: combining 3+ pieces depends on order.
  Matters once mitra-core uses the crate (decision 14).
- `t_judged_rejects_bad_confidence` and `t_rejects_invalid_masses` have no
  `test` declaration (no claim about `judged` or input checks yet).
- `--rev=X` is a usage error; short hashes compare as text.
