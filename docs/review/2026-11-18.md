## Trajectory

A reading of where the project stands after one day, for the decision to
continue. It weighs what is built, not what the vision says.

**How much of the vision was prototyped.**

| Vision item | State |
|---|---|
| Language: subjects, specs, claims, evidence, tests, profiles, policies | built, at confidence 0 and 1 |
| Verdict: logic, coverage, belief | built; belief is trivial (`strict`, `coverage`) |
| Golden set as the specification | built: 62 hand-written cases |
| Parser, printer, grammar checks, fuzzer, tree-sitter | built |
| Store, `add`, `ingest` of test reports, `--rev` | built; staleness is crude |
| Model next to the code | built for Rust comments |

| `next`: what to check | built, not useful yet |
| Diagnosis, root cause, conflicts ranked | not started |
| Hypotheses (uniformity), tests as subjects | design only |
| Structure: `uses`, glue claims | design only |
| Proofs as evidence, trusted base | not started |
| Requirements and traceability | design only |
| Elaboration (an LLM proposes, Mitra checks) | design only |
| The engine itself proven (Verus, Lean) | not started |
| Field trials, success criteria measured | planned, none run |

Roughly: the base layer is built and tested; every item that would
separate Mitra from a test runner with a coverage report is design or
nothing.

**Is the vision holding?** It has not been tested yet. Nothing built
contradicts it, and nothing built supports it. The prototype covers the
extremes, where the answer is known in advance. The dogfood shows what
the extremes are worth alone: nothing a developer would act on. The core
hypothesis (written-down hypotheses plus weighed evidence beat a
developer's guess) lives entirely in items not built.

**Are the results encouraging?** Mixed.

- For: real code was modelled one-to-one in about an hour, in a language
  that changed three times in the day without breaking the golden set. A
  spec written in Mitra matched its Rust function exactly. Each increment
  survived a red team that found real faults, so the base is sounder than
  a one-day prototype usually is. The model-above-function check is a
  small, real link between claims and code.
- Against: on 11 deliberate breaks, Mitra never said more than
  `cargo test`, said less on half, and named the wrong function once.
  Every verdict on real code is "uncertain, belief 0". The language cannot
  yet say a mass is one value, or that a test sampled its inputs.

**Is there a differentiated place?** The place described in
research/wedge.md (a ledger for code written with agents, that says what
green tests and "verified" really rest on) still looks unoccupied, but the
prototype does not stand in it yet. What it has that others lack is small:
exact input sets per claim, and specs as executable oracles. The
differentiating parts (weighing, conflicts, the trusted base of proofs)
are the unbuilt ones, so differentiation is unproven, not disproven.

**Effort still to do, at today's pace.** One day gave about ten
increments of code, each built, red-teamed and fixed in under an hour;
design decisions, which need you, set the pace more than coding did.

| Item | Estimate | Uncertainty |
|---|---|---|
| Failures count; `diag`; `next` rewritten (1, 2) | half a day | low |
| `uses` and suspects (4) | half a day to one day | medium |

| Success criteria measured (calibration, escaped defects) | months of real use | not compressible |

So a Mitra that could be judged fairly (graded belief, diagnosis, proofs
read) is about one to two weeks away at this pace, with the calculus as
the main unknown. Whether it is *worth* having cannot be known sooner than
the trials allow.

**Result (increment 9).** (a) is met: 8 of 8. (b) is half met: the broken

## Decisions taken alone

1. **Verdict output** prints `domain := Bool`, not `univ` as the design doc
   sketched: the type name says more.
2. **Golden files were converted by a program** (old parser + new printer),
   keeping comments. Expected results were translated by a script, so the
   values are the hand-written ones; only their spelling changed.
3. ~~Unicode only~~: superseded on 2026-11-17 evening, ASCII is now
   canonical (see decision 19).
4. **`evidence c at 1`** with no arguments means the claim on its whole
   domain (was `c(_, _) holds`).
5. **`f args = g`** with a bare function name `g` still means `g` applied to
   the same inputs. It is not Lean-like; kept because the evaluator has it.

6. **Store layout**: one `.mitra/` folder with `model.mitra` and one
   append-only `evidence.mitra`, merged by git's `union` driver, rather than
   the `.mitra/evidence/` folder or git notes in workflow.md. Simplest that
   merges cleanly.
7. **Provenance as Lean-style attributes**: `@[source "ci", rev "3f2a"]
   evidence …`. Recorded, not used by verdicts yet (no staleness yet).
8. **`mitra add` does not read git**: `--rev` is explicit. Predictable, and
   no hidden dependency on git.

9. **Tests are declared in the model**: `test t : <judgment>` (same
   judgment syntax as evidence). Since increment 8 the declaration can sit
   in a `// mitra:` comment above the test (decision 20).
10. **A failed test over a set gives no evidence** (only a note): Mitra has
    no "wrong somewhere in S" yet (composition.md open question 2). A failed
    `f x = v` test gives nothing either.
11. **Test names** are the last `::` segment of the report's path, so two
    tests with the same short name in different modules collide.

12. **`mitra next` is simple**: per uncertain claim, the missing inputs and
    up to 5 evidence lines to write; no ranking across claims yet, no
    weighting by profile.

13. ~~mitra-ds models masses as numbered cases~~: superseded by
    increment 8, a mass is three `Float64`s.
14. **mitra-core does not use mitra-ds yet**: intermediate confidences are
    still rejected. The calculus is not chosen (DS + Yager is only the
    recommendation), so wiring it in is left for a decision with you.

15. **Staleness, first cut**: `--rev R` on `check`/`eval`/`next` leaves out
    evidence recorded at any other revision. Crude (every commit makes all
    earlier evidence stale, even for subjects that did not change), but
    safe. The design's per-subject content hash needs subjects linked to
    code, which Mitra doesn't have yet.

16. **A failed negative test gives no evidence** (`test t : ¬ correct (f 1)`
    failing does not mean `correct (f 1)`: the test may have failed for
    another reason). A test listed twice in one report is left out.

17. **`--rev R` counts only evidence recorded at `R`**, including leaving
    out evidence with no `rev`. The first cut kept rev-less evidence, and
    the red team showed an old manual pass could then hide a newer failure
    (the failure, at another revision, was left out). Safe but blunt:
    manual evidence must carry `--rev` to count under `--rev`.
18. **The dogfood revision is the hash of the crate's code**, not the
    commit: committing the evidence file then doesn't make it stale.

19. **ASCII syntax, ranges, number types** (agreed with you, 2026-11-17
    evening): `forall in not | &` canonical with Unicode aliases; `0..=10`
    and friends replace `Icc`; `Int` is ℤ, plus `Int8`…`Int64`,
    `UInt8`…`UInt32`, `Float64`; `Real` reserved. Taken alone on top:
    `not` is now a keyword, so the golden subject `not` became `flip`
    (`tests/golden/flip/`); products print as a tuple of sets,
    `(0..=2, -2..=0)`; range bounds may pass 64 bits (values can't); a
    range equal to a fixed-width type prints its name (`-128..=127` is
    `Int8`); float `==` compares exactly (`NaN == NaN`).

20. **Rust model lines** (agreed with you, 2026-11-17 evening): in a
    store, `/// mitra:` and `// mitra:` comments under `src/` and `tests/`
    are part of the model, after `model.mitra`. Taken alone: an `opaque f`
    or `test t` must sit above `fn f` or `fn t` (an error otherwise), so a
    declaration can't drift from its code; claims, specs and policies may
    sit anywhere. Only Rust, only `fn` names, matched as text.
21. **mitra-ds's evidence was reset**: the old evidence named the numbered
    cases, which no longer exist. The append-only rule holds within a
    model, not across a rewrite of it.

22. **Uniformity is a claim with classes** (you asked for the claim,
    2026-11-18; the form is mine): `claim u : uniform f by g`, where the
    spec `g` sorts the inputs into classes. Not `uniform f on <set>` as
    sketched in chat: mitra-ds's regions are "both masses valid", "total
    conflict", which are predicates on floats, not boxes; a spec says
    both. Taken alone: at most 64 classes; one uniformity claim per
    subject; it counts only once evidence vouches for it; the verdict
    keeps `covered` (tested) apart from `assumed`.
23. **A pass and a failure in one class is a conflict** (your rule): the
    uniformity claim fails, the output shows both pieces of evidence, and
    Mitra does not pick the wrong one. Taken alone: a broken uniformity
    claim changes no other verdict, so the failure still refutes its own
    input and the pass still covers its own. A failure alone, under a
    uniformity claim that holds, refutes its whole class.
24. **A failed `f x = v` test refutes the `=` claims that give `v` at x**
    (`not c x`), so float output tests now count when they fail.
25. **Vouching by me**: mitra-ds's five uniformity claims carry
    `source "review:claude"`. I compared each class spec with the
    branches of its function. Your own review should replace mine.

26. **`uses` is a claim that only gives hints** (you asked for the claim,
    2026-11-18; the rest is mine): `claim n : uses f [g, h]`. It changes
    no verdict. Mitra follows it, through several levels, to name the
    failing subjects `f` relies on as suspects, and `next` prints the
    claims with no suspect first. It is used unless evidence denies it,
    so it needs no vouching: a wrong `uses` only misdirects a hint.
    Nothing checks it against the code yet. `only uses` is not built.
27. **Uniformity works per statement** (after the red team): `correct` is
    one statement and each `= e` another; claims with the same statement
    share their judged inputs, also outside their domains. A pass for
    `correct` and a failure for `= e` in one class is not a conflict.

28. **A contradicted input is reported** (you asked, 2026-11-18): each pair
    of pieces of evidence that pass and fail the same input prints as a
    conflict. Taken alone: the verdict rule is unchanged (the input counts
    on neither side, as in your extreme rule "contradiction at 1 →
    uncertain"), and nothing is assumed for the class of such an input.
    The contradiction cases of the golden sets gained their conflict
    lines; I checked each by eye, the lines were appended by Mitra.
29. **`only uses`, and trust without a vouch** (awaiting your answer, in
    chat). Shipped behaviour, the coordinator's proposal: an unvouched
    claim may raise suspicion but never trust. So `uses` and `only uses`
    give suspects unless denied; a root cause ("the fault is in `f`
    itself") needs `only uses` vouched; `next` lists unvouched ones. This
    replaces decision 26's "needs no vouching". "Only uses" means no
    other *subject*: private helpers are part of the function's own code.

30. **Several pieces can be wrong at once** (semantics question 1, still
    open). The ranking weighs every way of calling each piece right or
    wrong, not "which one piece". With one culprit, a failure that both
    refutes a claim and conflicts with a pass was blamed with certainty.
    Cost: 2^k for k pieces with a bias strictly between 0 and 1 in one
    group of errors, capped at 20, then "too many pieces to rank".
31. **The code is a piece.** A failing claim is weighed as {code of `f`,
    code of what `f` uses, the refuting evidence}. A claim on specs alone
    uses the claim itself.
32. **Dempster, conflict always shown** (question 2, open). When every
    piece is trusted at 1, nothing is ranked and the error says so.
33. **Display defaults: 5 candidates, threshold 0.05** (question 4,
    proposed): `--candidates`, `--threshold`, `--all`.
34. **`eval` exits 1 on errors** and prints the counts of errors and
    warnings on stderr. Warnings never change the status.
35. **Golden cases were regenerated, then read case by case.** Only the
    three `bias` cases have expected files written by hand first, with
    the arithmetic in their comments. The set is flattened to
    `tests/golden/<set>/<case>/`; the `by_usage` copies are gone.
36. **Removed from the language:** `policy`, `profile`, and the keywords
    `for`, `strict`, `coverage`. A bias is any number from 0 to 1.

### 16. Parameters and calls with parentheses, `->` for the result

Your decision: "go with parentheses everywhere and -> Value".

```lean
-- before
opaque judged (ok : Bool) (c : Float64) : Value
claim judged_ok : forall c in 0..=1, correct (judged true c)
evidence div 4 (-2) = -2 at 1

-- after
opaque judged(ok: Bool, c: Float64) -> Value
claim judged_ok : forall c in 0..=1, correct(judged(true, c))
evidence div(4, -2) = -2 at 1
```

The parser, the printer, the reports, the three grammars (LALR, LL(1),
tree-sitter), every golden case, the mitra-ds model and the docs changed
together. The old syntax is not accepted any more. The grammar is still
LL(1): the conflict checks and the fuzzer pass. Increments 1 to 15 above
keep their examples as they were written.

43. **Kept as they were**, because they are not calls or would not read
    better with parentheses. To settle, each one:
    - `evidence u at 1`: a judgment on a whole claim has no parentheses
      (`u()` is not accepted); on part of it, `evidence u(1, 2) at 1`.
    - `claim c : uniform f by g`, `claim c : uses f [g, h]`,
      `claim c : only uses f [g, h]`: names, not calls.
    - `claim c : … := by derive [p, q]`: Lean's tactic form.
    - `forall x in S,`: Lean's binder, with the trailing comma.
    - `claim name : …` and `test name : …` keep the `:` before the
      statement, while a result type now takes `->`.
    - `def f(x: Int) -> Int := e`: `:=` as in Lean, not `=` or braces.
    - `let x := e; body` and `if c then a else b` in expressions.
    - `@[source "who", rev "3f2a"]` before `evidence`.
