## Trajectory

A reading of where the project stands after one day, for the decision to
continue. It weighs what is built, not what the vision says.

**How much of the vision was prototyped.**

| Vision item | State |
|---|---|
| Language: subjects, specs, claims, evidence, tests, profiles, policies | built, at confidence 0 and 1 |
| Verdict: logic, coverage, belief | built; belief is trivial (`strict`, `coverage`) |
| Golden set as the specification | built: 62 hand-written cases |
| Parser, printer, grammar checks, fuzzer, tree-sitter | built |
| Store, `add`, `ingest` of test reports, `--rev` | built; staleness is crude |

| The engine itself proven (Verus, Lean) | not started |
| Field trials, success criteria measured | planned, none run |

Roughly: the base layer is built and tested; every item that would
separate Mitra from a test runner with a coverage report is design or
nothing.

**Is the vision holding?** It has not been tested yet. Nothing built
contradicts it, and nothing built supports it. The prototype covers the
extremes, where the answer is known in advance. The dogfood shows what
the extremes are worth alone: nothing a developer would act on. The core
hypothesis (written-down hypotheses plus weighed evidence beat a
developer's guess) lives entirely in items not built.

**Are the results encouraging?** Mixed.

- For: real code was modelled one-to-one in about an hour, in a language
  that changed three times in the day without breaking the golden set. A
  spec written in Mitra matched its Rust function exactly. Each increment
  survived a red team that found real faults, so the base is sounder than
  a one-day prototype usually is. The model-above-function check is a
  small, real link between claims and code.
- Against: on 11 deliberate breaks, Mitra never said more than
  `cargo test`, said less on half, and named the wrong function once.
  Every verdict on real code is "uncertain, belief 0". The language cannot
  yet say a mass is one value, or that a test sampled its inputs.

**Is there a differentiated place?** The place described in
research/wedge.md (a ledger for code written with agents, that says what
green tests and "verified" really rest on) still looks unoccupied, but the
prototype does not stand in it yet. What it has that others lack is small:
exact input sets per claim, and specs as executable oracles. The
differentiating parts (weighing, conflicts, the trusted base of proofs)
are the unbuilt ones, so differentiation is unproven, not disproven.

**Effort still to do, at today's pace.** One day gave about ten
increments of code, each built, red-teamed and fixed in under an hour;
design decisions, which need you, set the pace more than coding did.

| Item | Estimate | Uncertainty |

| `uses` and suspects (4) | half a day to one day | medium |

So a Mitra that could be judged fairly (graded belief, diagnosis, proofs
read) is about one to two weeks away at this pace, with the calculus as
the main unknown. Whether it is *worth* having cannot be known sooner than
the trials allow.

**Result (increment 9).** (a) is met: 8 of 8. (b) is half met: the broken

## Decisions taken alone

1. **Verdict output** prints `domain := Bool`, not `univ` as the design doc
   sketched: the type name says more.
2. **Golden files were converted by a program** (old parser + new printer),
   keeping comments. Expected results were translated by a script, so the
   values are the hand-written ones; only their spelling changed.
3. ~~Unicode only~~: superseded on 2026-11-17 evening, ASCII is now
   canonical (see decision 19).
4. **`evidence c at 1`** with no arguments means the claim on its whole
   domain (was `c(_, _) holds`).
5. **`f args = g`** with a bare function name `g` still means `g` applied to
   the same inputs. It is not Lean-like; kept because the evaluator has it.

6. **Store layout**: one `.mitra/` folder with `model.mitra` and one
   append-only `evidence.mitra`, merged by git's `union` driver, rather than
   the `.mitra/evidence/` folder or git notes in workflow.md. Simplest that
   merges cleanly.
7. **Provenance as Lean-style attributes**: `@[source "ci", rev "3f2a"]
   evidence …`. Recorded, not used by verdicts yet (no staleness yet).
8. **`mitra add` does not read git**: `--rev` is explicit. Predictable, and
   no hidden dependency on git.

9. **Tests are declared in the model**: `test t : <judgment>` (same
   judgment syntax as evidence). Since increment 8 the declaration can sit
   in a `// mitra:` comment above the test (decision 20).
10. **A failed test over a set gives no evidence** (only a note): Mitra has
    no "wrong somewhere in S" yet (composition.md open question 2). A failed
    `f x = v` test gives nothing either.
11. **Test names** are the last `::` segment of the report's path, so two
    tests with the same short name in different modules collide.

12. **`mitra next` is simple**: per uncertain claim, the missing inputs and
    up to 5 evidence lines to write; no ranking across claims yet, no
    weighting by profile.

13. ~~mitra-ds models masses as numbered cases~~: superseded by
    increment 8, a mass is three `Float64`s.
14. **mitra-core does not use mitra-ds yet**: intermediate confidences are
    still rejected. The calculus is not chosen (DS + Yager is only the
    recommendation), so wiring it in is left for a decision with you.

15. **Staleness, first cut**: `--rev R` on `check`/`eval`/`next` leaves out
    evidence recorded at any other revision. Crude (every commit makes all
    earlier evidence stale, even for subjects that did not change), but
    safe. The design's per-subject content hash needs subjects linked to
    code, which Mitra doesn't have yet.

16. **A failed negative test gives no evidence** (`test t : ¬ correct (f 1)`
    failing does not mean `correct (f 1)`: the test may have failed for
    another reason). A test listed twice in one report is left out.

17. **`--rev R` counts only evidence recorded at `R`**, including leaving
    out evidence with no `rev`. The first cut kept rev-less evidence, and
    the red team showed an old manual pass could then hide a newer failure
    (the failure, at another revision, was left out). Safe but blunt:
    manual evidence must carry `--rev` to count under `--rev`.
18. **The dogfood revision is the hash of the crate's code**, not the
    commit: committing the evidence file then doesn't make it stale.

19. **ASCII syntax, ranges, number types** (agreed with you, 2026-11-17
    evening): `forall in not | &` canonical with Unicode aliases; `0..=10`
    and friends replace `Icc`; `Int` is ℤ, plus `Int8`…`Int64`,
    `UInt8`…`UInt32`, `Float64`; `Real` reserved. Taken alone on top:
    `not` is now a keyword, so the golden subject `not` became `flip`
    (`tests/golden/flip/`); products print as a tuple of sets,
    `(0..=2, -2..=0)`; range bounds may pass 64 bits (values can't); a
    range equal to a fixed-width type prints its name (`-128..=127` is
    `Int8`); float `==` compares exactly (`NaN == NaN`).

20. **Rust model lines** (agreed with you, 2026-11-17 evening): in a
    store, `/// mitra:` and `// mitra:` comments under `src/` and `tests/`
    are part of the model, after `model.mitra`. Taken alone: an `opaque f`
    or `test t` must sit above `fn f` or `fn t` (an error otherwise), so a
    declaration can't drift from its code; claims, specs and policies may
    sit anywhere. Only Rust, only `fn` names, matched as text.
21. **mitra-ds's evidence was reset**: the old evidence named the numbered
    cases, which no longer exist. The append-only rule holds within a
    model, not across a rewrite of it.

22. **Uniformity is a claim with classes** (you asked for the claim,
    2026-11-18; the form is mine): `claim u : uniform f by g`, where the
    spec `g` sorts the inputs into classes. Not `uniform f on <set>` as
    sketched in chat: mitra-ds's regions are "both masses valid", "total
    conflict", which are predicates on floats, not boxes; a spec says
    both. Taken alone: at most 64 classes; one uniformity claim per
    subject; it counts only once evidence vouches for it; the verdict
    keeps `covered` (tested) apart from `assumed`.
23. **A pass and a failure in one class is a conflict** (your rule): the
    uniformity claim fails, the output shows both pieces of evidence, and
    Mitra does not pick the wrong one. Taken alone: a broken uniformity
    claim changes no other verdict, so the failure still refutes its own
    input and the pass still covers its own. A failure alone, under a
    uniformity claim that holds, refutes its whole class.
24. **A failed `f x = v` test refutes the `=` claims that give `v` at x**
    (`not c x`), so float output tests now count when they fail.
25. **Vouching by me**: mitra-ds's five uniformity claims carry
    `source "review:claude"`. I compared each class spec with the
    branches of its function. Your own review should replace mine.

26. **`uses` is a claim that only gives hints** (you asked for the claim,
    2026-11-18; the rest is mine): `claim n : uses f [g, h]`. It changes
    no verdict. Mitra follows it, through several levels, to name the
    failing subjects `f` relies on as suspects, and `next` prints the
    claims with no suspect first. It is used unless evidence denies it,
    so it needs no vouching: a wrong `uses` only misdirects a hint.
    Nothing checks it against the code yet. `only uses` is not built.
27. **Uniformity works per statement** (after the red team): `correct` is
    one statement and each `= e` another; claims with the same statement
    share their judged inputs, also outside their domains. A pass for
    `correct` and a failure for `= e` in one class is not a conflict.

28. **A contradicted input is reported** (you asked, 2026-11-18): each pair
    of pieces of evidence that pass and fail the same input prints as a
    conflict. Taken alone: the verdict rule is unchanged (the input counts
    on neither side, as in your extreme rule "contradiction at 1 →
    uncertain"), and nothing is assumed for the class of such an input.
    The contradiction cases of the golden sets gained their conflict
    lines; I checked each by eye, the lines were appended by Mitra.
29. **`only uses`, and trust without a vouch** (awaiting your answer, in
    chat). Shipped behaviour, the coordinator's proposal: an unvouched
    claim may raise suspicion but never trust. So `uses` and `only uses`
    give suspects unless denied; a root cause ("the fault is in `f`
    itself") needs `only uses` vouched; `next` lists unvouched ones. This
    replaces decision 26's "needs no vouching". "Only uses" means no
    other *subject*: private helpers are part of the function's own code.

30. **Several pieces can be wrong at once** (semantics question 1, still
    open). The ranking weighs every way of calling each piece right or
    wrong, not "which one piece". With one culprit, a failure that both
    refutes a claim and conflicts with a pass was blamed with certainty.
    Cost: 2^k for k pieces with a bias strictly between 0 and 1 in one
    group of errors, capped at 20, then "too many pieces to rank".
31. **The code is a piece.** A failing claim is weighed as {code of `f`,
    code of what `f` uses, the refuting evidence}. A claim on specs alone
    uses the claim itself.
32. **Dempster, conflict always shown** (question 2, open). When every
    piece is trusted at 1, nothing is ranked and the error says so.
33. **Display defaults: 5 candidates, threshold 0.05** (question 4,
    proposed): `--candidates`, `--threshold`, `--all`.
34. **`eval` exits 1 on errors** and prints the counts of errors and
    warnings on stderr. Warnings never change the status.
35. **Golden cases were regenerated, then read case by case.** Only the
    three `bias` cases have expected files written by hand first, with
    the arithmetic in their comments. The set is flattened to
    `tests/golden/<set>/<case>/`; the `by_usage` copies are gone.
36. **Removed from the language:** `policy`, `profile`, and the keywords
    `for`, `strict`, `coverage`. A bias is any number from 0 to 1.


Taken alone:

93. **A set sees a recursive type one level deep.** Inside itself the
    type is `Value` for the set algebra; each value is checked all the
    way down, against the type as declared. So `Add(Lit(1), 2)` is

    automata), a large change to the set algebra for the same verdicts,
    since such a type is infinite and only classes or a proof cover it.
94. **Recursion must go down.** A spec calls itself only on a piece of
    one parameter, the same one in every call: bound by `match`, a
    field, an element. Refused: `down(n - 1)` on integers, two specs
    calling each other, two types containing each other. Open: recursion
    on integers with a bound (`0..`) is the common missing case.

    of `rate(x in S, cond)`**: `all(x in xs, cond)`. The names are not
    keywords; a function of yours named `map` still works. Alternatives:
    Rust closures `xs.iter().all(|x| …)` (needs methods and `|x|`), Lean
    `xs.all fun x => …` (needs `fun`). Both add a surface form; this one
    adds none, at the price that the first argument binds a name.
    If function types come (the "minimal kit"), these five become
    ordinary functions taking a function, and this form can go or stay
    as sugar: nothing here blocks it.
96. **`fold(x in xs, let acc := start; step)`** reuses `let` for the
    running value. It reads oddly: `let` is set again for each element.
    Alternatives: `fold(x in xs, acc := start, step)` (a new form in an
    argument), or only `sum`, `count`, `max` and no `fold`. This is the
    one I am least sure of.
97. **Over a set, `map` and `filter` give a set.** Over a map: refused,
    use `keys(m)`.
98. **A value is nested 64 deep at most**, to stop a stack overflow on
    input.

Found on the way, fixed: counting the values of a set listed a nested
value again at every level, so one input nested 15 deep took over a
minute; the same list term twice in a set printed twice (`List(Value) |
List(Value)`).

- A spec that builds a value deeper than 64 through `fold` is not stopped.
- With classes over an infinite type, nothing checks that the classes

### 26. The rest of the kit: type parameters and function types

Your "we need the minimal kit". With increment 25 the kit is: base types,
records and tuples, enums, recursion, type parameters on enums, records
and functions, function types.

```lean
record Pair(A, B)(first: A, second: B)
def first(T)(xs: List(T)) -> Option(T) := if len(xs) == 0 then None else Some(xs[0])
def double(x: Int) -> Int := x * 2
opaque apply(f: (Int) -> Int, x: Int) -> Int
claim apply_is : forall f, forall x, apply(f, x) = f(x)
evidence apply(double, 3) = 6 at 1
```

Grammar: one optional `(T, …)` after the name of a record or a function,
and `-> type` after a parenthesised type. No keyword.

Taken alone:

99. **Type parameters are written like those of `enum`**: in
    parentheses, before the fields or the parameters. Two groups of
    parentheses in a row read poorly (`swap(A, B)(p: …)`). Alternatives:
    Rust `swap<A, B>(p: …)`, Lean `swap {A B} (p : …)`. I kept the form
    enums already had so that there is one; changing all three together
    is a small change if you pick another.
100. **A record with type parameters is an enum of one variant**, inside:
    one mechanism. So it is declared above its first use, and
    `Pair(Int, String)` gives its parameters, while on a plain record
    `Number(Int, {"m"})` gives a set for each field. Same writing, two
    meanings: this is a real inconsistency, kept because both existed.
101. **In a function, a type parameter is any value.** `first(T)` is not
    checked to return the `T` it was given. Alternative: check that the
    values at `T` in the result come from the values at `T` in the
    inputs. True for Rust without trait bounds, false with them
    (`T: Default`), so not done.
102. **A function type is the finite set of the functions declared above
    that fit.** No closure, no anonymous function: a function value is a
    name. Consequences: the function passed must be declared above the
    function that takes it, and a claim over `f` lists the model's
    functions (`no evidence on f in {negate}`). Alternative: all
    functions of the model, wherever declared (needs two passes), or
    anonymous functions (a new form, and no finite set).
103. **Written `(A, B) -> C`**, the shape of a declaration, not Rust's
    `Fn(A, B) -> C`. The result is one type, parentheses for a union.
104. **Inside a function type a type parameter accepts every function**:
    in `each(T, U)(xs: List(T), f: (T) -> U)`, `f` is any function of
    one parameter. Nothing checks that `f` accepts the elements of `xs`
    until it is called on one.
105. **The list functions stay as they are**: `map(x in xs, f(x))`. I
    did not add `map(xs, f)`: one way to write it.
106. **A recursive enum needs one variant that is not itself alone**:
    `Node(value: T, next: Option(Node(T)))` is fine, `More(next: Loop)`
    alone is refused (corrects the rule of increment 25).

Open:

- The printer writes a function type as its set, `{double, negate}`. It
  reads back the same, but loses what was written.
- Built-ins are not redefined on the kit (`Bool`, `Option`, `List`,
  tuples, unit): waiting for your go.
- Nothing for IO or operations whose result is not determined.

### 27. The reworked language, stage 1: a new surface on the same engine

Your frame (subject, properties, boundary, evidence, simulation) and the
rule "every declaration is `keyword name(inputs) -> Output { body }`".
Reference: [docs/reference/reworked.md](../reference/reworked.md).

```rust
subject loader {
    fn load(url: {"a", "b"}) -> Config uses network::fetch, parse;
    claim falls_back(url: {"a", "b"}) when network::fetch(url) is Err {
        load(url) == default_config()
    }
}
evidence a_falls_back { for loader::load  given url = "a"  gives Config(3, false) }
```

How it is built: `crates/mitra-core/src/surface.rs` translates each
declaration to the earlier syntax, on the same line, and the engine is
unchanged except one point (decision 112). Both syntaxes are read. This is
a prototype to try the language by hand, not the final implementation.

Staging I propose:

1. **This increment**: the surface. Subjects, boundaries, `fn` with or
   without body, claims with inputs and `when`, `assume`, `uses`,
   `uniform`, Rust-like types and expressions, evidence blocks, tests.
2. Claims with parameters as a library (`uniform`, `represented` written
   in Mitra; inline functions, set comprehension, `correct` as a Bool,
   `mitra explain <claim>`); a spec standing in for its code; a vouched
   property passing observations on.
3. Boundary semantics: answers that differ each time, distributions,
   `holds assuming [assumption]`, simulations, sequences.
4. Move the golden cases, the dogfooding stores and the grammars to the
   new syntax, then remove the earlier one. Verdict lines, `mitra next`
   and stored evidence print the new syntax.

Taken alone:

107. **A front end that translates, not a second engine.** Fast to try
     and to change. Cost: verdict lines and `mitra next` still print the
     earlier syntax and generated names. Alternative: a new AST straight
     away (stage 4).
108. **Names are `subject::name`**, and inside a subject a sibling is
     named without the prefix. Evidence may name the last part alone when
     only one function or claim has it (`for fetch`).
109. (Reversed by increment 55: scoped to their block.) **Records, enums and variants are global**, even written inside a
     subject. Alternative: `pair::Pair`; heavier to write in every value.
110. **A body in a subject is a spec and a claim.** `fn add(…) { … }` in
     a subject gives the opaque code `pair::add`, and the claim
     `pair::add::spec` that the code returns what the body returns. It is
     unverified until outputs are observed. Outside any subject, a body
     is a plain helper with no code behind it. Alternative: a keyword
     (`spec fn`), or always a claim.
111. **`uses` is taken as declared**: the clause adds the claim
     `f::uses` with its own evidence (source `declared`), so it holds
     without a review. Alternative: unverified until someone vouches, as
     in the earlier syntax.
112. **`when` on the inputs alone removes inputs from the claim** (your
     condition: domain = given minus when). Done for finite input sets
     only, by one hook in the engine (`eval.rs`, a hidden function
     `claim::when`). On an infinite set, and when `when` reads what the
     code returned, it is an implication: inputs refused by `when` count
     as passing. To redo properly in stage 2.
113. **`assume` is a claim that brings its own evidence** (trust 1,
     source `assumed`). So it prints `holds`, and what depends on it does
     not yet print `holds assuming [it]`. Evidence against it is an
     error with both pieces as candidates. A boundary is otherwise a
     subject: nothing yet for answers that differ each time.
114. **`given` both ways**: inputs in parentheses with `when` before the
     braces, or `given … when … then …` inside the braces. You may want
     only one.
115. **`uniform(f, |a, b| class)` is built in for now**, with the class
     a Bool by default and `|m| -> Type { class }` otherwise: the engine
     needs the finite list of classes. `represented` is not there.
116. **Evidence block**: `for`, `given a = v, b in Set`, `holds` /
     `fails` / `gives value` / `gives rate = n`, `trust`, `source`
     (default: the block's name), `rev`. Inputs are given by name; one
     left out means every value. Alternative for sets: `given b: Set`
     (also accepted).
117. **Tests are the same block with `test`**, in the model:
     `test t { for add  given left = 2, right = 2  gives 4 }`.
118. **Types**: Rust's names are aliases (`bool`, `i32`, `Vec<T>`,
     `u64` = `0..`); generics with `<T>`; `fn(A) -> B`. `Option` and
     `Result` must still be declared as enums.
119. **Expressions**: `if c { a } else { b }`, `let x = e;`, `==`, and
     `<=>` for "both or neither" (same as `==` on Bools). `x is Variant`
     ignores the fields.
120. **A file is in one syntax**, detected from its content (`opaque`,
     `def`, `:=` or `claim name :` mean the earlier one). The evidence
     file of a new model may mix blocks and earlier lines, because
     `mitra add` and `mitra ingest` still append earlier lines.
121. **`--` at the start of a line is still a comment** in the new
     syntax, so that the files `mitra init` writes are read.

Open, found while building:

- Keywords of the earlier syntax can't be names (`by`, `at`, `from`,
  `not`, `correct`, …): the error names the word and the line.
- `claim c(folder) { route(Spam, folder) == "junk" }` stays unverified
  although `route` has a body that settles it: the spec does not stand
  in for the code (stage 2, propagation).
- A class written inline prints as `claim_name::case` in verdicts.
- `correct(…)` under `when` is refused; narrow the input type instead.
- Order, sequences and simulations: no syntax chosen.
- Your rule "everything can be a suspect". Today the candidates of a
  conflict are evidence, the code of a subject, and a claim that is
  vouched or assumed. In this prototype `assume` and `uses` come in as
  evidence with a source (`assumed`, `declared`) and trust 1, so they
  already appear as candidates. Not suspects yet: a claim's own
  statement, a spec body, a signature. Evidence outside a declared type
  is refused when read, not kept as a conflict.

What is built: outputs a claim does not have come from a vouched claim

Decisions taken alone:

138. **A claim follows from the specs of what it calls only when they
     imply it on every input.** Alternative: as with `by derive`, accept
     it when the implication could not be checked. Refused: nobody wrote

139. **(Replaced by M007, increment 30.) A claim the specs contradict is only `not derived`.** It can
     still hold through other evidence (in `examples/reworked/clock`,
     `wrong` holds through `next_uniform`). The right answer is an error
     between the claim and the spec; not built. Open.
140. **A vouched claim `f(…) == e` gives outputs to every other claim**,
     in both syntaxes. This changed 7 goldens of `compose` and `minus`:
     a derived claim whose leaf is wrong now **fails** on the exact input
     (`minus_spec fails on minus(1, 1)`) where it was `unverified`, and
     `assumed on …: its premises imply it` becomes `passes on` where the

     only. Kept for both: it is the same engine, and the result is more

142. **The vouch must be on the whole claim and nowhere denied** to give
     outputs. A vouch on part of the inputs gives nothing.
143. **A claim never uses its own vouch to get an output** (it would
     pass on every input for free). It still holds through the vouch as
     before.
144. **A claim with parameters is told from a claim by its shape**:
     every name in the parentheses without a type, and a body starting

     keyword because you wrote it as `claim uniform(f, case) { given … }`.
     Before this, that shape was a claim with untyped inputs plus
     `given`; nothing used it.
145. **Parameters are replaced as written** (a macro), then the claim is
     read where it is used: an error in the body shows on the line of the
     use. A parameter can stand for a function, a set, a value or an
     inline function, also in a type position.
146. **A claim with parameters is declared above its uses**, and one
     written in a subject is found from that subject or by its bare name.
147. **An inline function exists only applied** `(|a| e)(x)`: it is not
     a value, and its inputs have no types. Enough for parameters; not
     closures in general.
148. **`{ x in xs | cond }` needs a source set.** `{ (a, b) | b != 0 }`
     over the inputs of a function, as in your `represented` example, is
     not a value Mitra can list, so it is not read.
149. **`represented` and `uniform` as library claims are not built.**
     Your definition relates `correct(f(x))` on two inputs; `correct` is
     a judgement on one piece of evidence in the engine, not a Bool.
     `represented(f, S)` also needs "one class, and nothing said outside
     it", which `uniform` can't say (the rest would be a second class).
     Both need a decision on the calculus, not only syntax.
150. **An assumption with only its own word prints
     `holds assuming [itself]`** and gives no warning. Alternatives:

     assumption (noise: it is written on purpose). Claims that read it

151. **An assumption is checked once observations cover its inputs**:
     then `holds` or `fails`, and the claims that read it follow.
     Assumptions are declared above the claims that read them.
152. **A boundary function with two outputs on one input: both stand**,
     and a claim is judged on every answer seen (fails if one breaks it).
     Mitra does not know the answers never seen: passing on the seen ones

     distributions would do.
153. **A boundary function is never a candidate** ("the code of

154. **A body can't call a boundary** (`fn left(t) { t - clock::now() }`

     uncertain operation, to be defined with simulations).
155. **`mitra explain <name>`** tries a code first, then a claim, by its
     full name or the part after the last `::`.
156. **`mitra next` writes evidence as blocks with `<name>` to fill**:

  the reports, and took evidence written on it. But on a record with
  finitely many values Mitra decided it alone over every value of the
  type (`p.x == p.y` failed on 90 of 100 points with no evidence), and
  no observed output touched it.
- mitra-core's model: the records are in `reader`, `types`,
  `verdicts`, `report`; `Model.claims: Vec<Claim>` is stated; the
  variant `Piece::Claim` and the record `reader::Claim` no longer
  clash (finding of 54).

Decisions taken alone:

291. **Enums and their variants are scoped too** (`report::Piece`,
     `report::Code`). Alternative: records only.
292. **Short name outside its block** when exactly one block has the
     name and nothing outside any block does; a top-level name wins.
     Alternative: always the full name outside, or `import`.
293. **In evidence**, `for block::f` makes short names those of
     `block`.
294. **Unnamed `subject { }` blocks do not scope**: their records are
     top-level, like their functions.
295. **Importing a scoped type from another file** is not built: the
     full name is written.
296. **A claim on a record is no longer decided over every value of
     the type**, only on observed outputs: it is `unverified` with the
     values seen, never `holds` alone. Alternative: keep deciding
     finite records alone (then it is a claim on the type, not on the
     code).
297. **Which claims**: one input, of a record type, calling no code.
     A claim on two records, or on a record and a function, is as
     before. Not derived for a record with contents left out as a
     whole (`record R;`): no value of it can be written in evidence.
298. **Which outputs**: those of functions whose result is the record
     itself, not one holding it (`Option<R>`, `Vec<R>`, an input).
299. **No implied correctness for records.** A function has code that
     can be wrong on its own; a record has only its shape (the tie)
     and what is built into it (the functions). `R::correct` would
     repeat `f::correct` of the builders. My view, not built either way.

Open: whether a claim on a record should hold once every function
returning it is correct (it would then follow, like claims on reached
functions); today nothing makes it `holds` but a vouch on it.

### 56. `impl` and `self`, as Rust writes them

Asked by the user: "let's take impl & self and follow Rust grammar and
syntax example".

```
subject geo {
    record Point { x: 0..=9, y: 0..=9 }
    impl Point {
        fn new(x: 0..=9, y: 0..=9) -> Self;                // geo::Point::new
        fn flip(&self) -> Self { Point(self.y, self.x) }   // a method
        claim on_the_diagonal(self) { self.x == self.y }   // a claim on the record
    }
    claim c(p: Point) { p.flip().flip() == p }
}
```

It is a way of writing: the reader turns `fn flip(&self)` into
`fn Point::flip(self: Point)` before anything else; the engine did not
change. Tie: `// mitra: implements geo::Point::flip` above the method
of the code. mitra-core's model uses it for `types::Model::check` and
`report::Logic::as_str`. `scripts/coverage.py` prints, per crate, "N
lines of model over M lines of code, in S subjects with E ensures and
R requires".

Decisions taken alone, each where Rust's form was taken or not:

300. **`&self`, `&mut self`, `mut self`** are read and mean `self`:
     Mitra has no references. `&T` in any other type is not read.
301. **`Self`** is the record, inside its `impl` only. `self: Self`
     (the typed form) is not read.
302. **A function without `self`** is called `Point::new(..)`, never
     as a method, like Rust.
303. **Which method `p.name()` is**: that of the record `p` is
     declared as, when `p` is an input with a type; on any other
     expression the only method of that name, else an error asking
     for `R::name(p)`. Mitra works out no type of an expression.
     Alternative: types of expressions, a real addition.
304. **`impl` on an enum** is read (`impl Logic`), and an `impl` may
     sit in another subject than its record, like in Rust's crate: the
     function is named by the subject of the `impl`
     (`report::Logic::as_str`, `Logic` being `verdicts::Logic`).
305. **Refused**: type parameters (`impl<T> Box<T>`), traits
     (`impl T for R`), an `impl` inside another.
306. **At top level** an `impl` follows the rule of a bare `fn`: its
     functions need a body.
307. **A claim in an `impl`** is named `R::claim`; `assume` too.
     `ensure` and `require` written there belong to the subject, with
     no other meaning.
308. **The tie reads `Self` in the code** as the type of the nearest
     `impl` line above.
309. **The size line** counts the lines starting with `subject`,
     `ensure`, `require` in the model files (points included);
     boundaries are not counted.

Not built, said by the user for later: softening decision 282 with
special claims on records and functions ("being sized, non-recursive").

### 57. Words of the language as names; what justifies a `require`

Asked by the user: "why not raw identifiers too? … you should probably
allow it when there is no ambiguity yes", and on M105 "as long as we
find something to justify the require inside the body of the subject,
it should be ok".

- A reserved word is a name as a field, after a dot, and (for the
  words that only start a declaration) as an input or a `let`.
  `r#word` everywhere else. The Rust inputs `ledger` of `load`, `read`
  and `run` are `evidence` again, and the model states `Verdict.claim`.
- M105 is silent when anything beside the `require` leans on the block
  of the promise: a `uses`, also through other blocks; a call in a body
  or in a claim; one of its types in a signature or a record field.
  In mitra-core `advice::judged` is now justified (it takes a
  `verdicts::Report`); `verdicts::computed` still warns, since
  `evaluate` declares no `uses` on `eval`, and mitra-ds's
  `culprits::combining` too (`rank` declares none). Both left as found.

Decisions taken alone:

310. **Which words are inputs without `r#`**: `record`, `fn`, `claim`,
     `evidence`, `enum`. Any other reserved word (`match`, `if`, `in`,
     `len`, a type name) starts an expression or a type, so as an
     input it is refused with "write `r#match`". Alternative: every
     word that happens to be unambiguous at that spot.
311. **`r#match` is the name `r#match`** in the model and in what is
     printed; only the tie treats it and `match` as one. Alternative:
     drop the `r#` after reading, as Rust does.
312. **"Through other functions"** is counted per block: s leans on
     mid, mid leans on mailer, so s leans on mailer.
313. **A call in a claim counts**, not only in a body: a claim
     comparing `f(u)` with `mailer::send(u)` leans on the mailer.
314. **A type counts when it is named** in a signature or a field of
     the block; a type only met inside another block's record does
     not.
315. **M106 unchanged**: a direct `uses` on a block that makes
     promises still asks for a `require`.

### 58. A test settles what it pins

Asked by the user: "the evidence provided from a test tie should be
pinned as much as possible. I think the ingest should warn that the
evidence is losing value by not stating what input is pinned", and
"yes sweep rule".

- A passing test tied to a claim with inputs, whose comment states
  none, is written `evidence test { for c passes … }`. `passes` is a
  new word of evidence: it shows under the claim (`passes on inputs
  not stated (test:name)`) and covers nothing. `ingest` warns, naming
  each such test. A failing one is still `fails` on the whole claim.
- The tie comment takes the clauses of an evidence block:
  `// mitra: evidence for div given a = 6, b = 2 gives 3`, on a
  function or on a claim, one comment per point.
- In Mitra's stores: `reader::fault_is_placed` and
  `verdicts::one_verdict_each` are `unverified` again (two sweeps),
  and seven tests of mitra-ds (redone in the remodelling).

Decisions taken alone:

316. **The word `passes`**, beside `holds` and `fails`. Alternatives:
     `holds somewhere`, or a trust below 1 on `holds` (rejected: trust
     never changes a verdict, the claim would still read `holds`).
317. **`passes` with no input to state is `holds`** (a claim or a
     function with no input); with `given` it is refused.
318. **A pinned test that fails** is written `given … fails`, on a
     function (the code is wrong there) or on a claim; what it was
     said to give is dropped.
319. **A pinned comment is not checked by `ingest` itself**: the block
     is read like any evidence, and a fault names the evidence line,
     not the Rust file.
320. **Nothing checks that the test does what its comment pins**: the
     comment is the author's word, like a vouch.
321. **`passes` does not enter the trust model**: it is never a
     candidate, since it contradicts nothing.

### 59. `deterministic(f)`, claimed by default

Asked by the user: "let's make deterministic(f) beside correct with
the by default rule too. It is better that we don't have implicit
assumptions in Mitra."

- Every function of a subject has the claim `f::deterministic`: the
  same input always gives the same output. `unverified` until someone
  vouches (`for f::deterministic holds`), `fails` when evidence shows
  two outputs on one input.
- Two outputs on one input were error M003 between the two pieces of
  evidence. They are now M001 on `f::deterministic`, with the code of
  `f` among the candidates. Neither output is relied on, as before.
- `claim same = deterministic(f) trust 0.9;` names it;
  `claim free = !deterministic(f);` says the function may answer
  differently: no implied claim, no contradiction, and it holds once
  two outputs differ.
- mitra-core's model has `verdicts::never_runs` again, with
  `claim same_report = deterministic(run);`.

**What it costs, to weigh.** One more line and one more warning per
function of a subject, in every model: a fully tested claim no longer
gives a clean report until someone vouches for determinism. Mitra's
stores gain 30 warnings (core 54 to 71, cli 12 to 19, ds 7 to 13). The alternative is a claim that exists only
once evidence or the model names it, like `f::tied`: quieter, but the
assumption is silent again until then.

Decisions taken alone:

322. **Unverified by default**, with warning M101, like `f::correct`.
     Alternative: `holds assuming [itself]`, named and quiet.
323. **What settles it**: a vouch only. Seeing the same output twice
     on one input is not counted as support.
324. **Functions with a body too**: the claim is on the code, the
     body is its spec.
325. **Claims that read an observed output do not list
     `f::deterministic` among what they assume.** Strictly they
     should: one observed output stands for every call. Not built:
     every verdict from a test would become `holds assuming`.
326. **`!deterministic(f)`** as the way to drop it, a claim with its
     own verdict. Alternative: a word on the function (`fn roll() ->
     1..=6 varies;`).
327. **Only the second output is shown** as "the evidence that says
     so"; both outputs are candidates.
328. **An `ensure` rests on the determinism claims of its block**,
     like on its other claims.

Other things the engine takes for granted, listed as asked, not
fixed:

- Evidence with no `trust` is trusted fully, a test's expected value
  included.
- Evidence is about the code as it is now, unless `--rev` is given.
- A helper of the model (a bare `fn` with a body) is right: never a
  candidate.
- The model's arithmetic is the code's (floats, overflow).
- A type of the model wider or narrower than the code's passes the
  tie (`0..=9` against `i64`).
- A function with no `uses` clause is not said to call nothing: it is
  simply not checked.
- What a tie comment pins is the author's word (decision 320).

### 60. The type of every expression, at `check`

Asked by the user: "build the type check expressions".

- `crates/mitra-core/src/types.rs`: a type is a set of values; the
  type of an expression is the set it can be. An expression is
  refused when that set never meets what its place takes. Examples of
  messages: "`+` takes `Int | Float64`, and `"x"` is `{"x"}`",
  "`g(a)` is `Int`, which has no `.size`", "`h`, as `s`, takes
  `String`, and `g(a)` is `Int`", "`c` is `Int`, never true or
  false", "`k` gives `Int`, never its result type `String`".
- A method call is resolved from the type of its receiver, whatever
  the expression: `pick(b).size()`, `b.a.size()`, `let a = …;
  a.size()`, `A(1).size()`.
- **What it flags in what exists: nothing.** The 112 goldens, the
  examples, the reference and the three models of Mitra all pass
  unchanged. One test changed its message (`all(x in [1], x + 1)`,
  refused before at evaluation, now at check).

Decisions taken alone:

329. **Refused only when it can never fit**: a wider type passes
     (`Int` where `0..=2` is taken), as a value of the right type may
     come. Alternative: refuse unless it always fits, which would
     refuse most models written with ranges.
330. **`Any` is "not known"**: nothing is refused on it. Elements of
     lists, results of `fold`, tuple positions (`t.0`), calls of
     functions with type parameters are `Any` for now.
331. **An integer and a float do not mix** in `+ - * /` and
     comparisons, as at evaluation.
332. **`==` and `!=` take anything**: comparing two types that never
     meet is not refused (it is false).
333. **By name where the type is not known**: `xs[0].size()` on a
     `List<Any>` still takes the only method named `size`, and asks
     for `R::size(…)` when there are two. Alternative: refuse.
334. **No error code**: these are faults of `check`, like an unknown
     name, with their line.

### 64. `uses` implied

Asked by the user: "use from calls that can be extracted from the body
should be implicitly extracted and added like correct and det no?";
"implied uses yes".

- **With a body and no `uses`**: the claim `f::uses` is implied as
  `uses only` the functions of the code and of the world the body
  calls. It is checked by `mitra tie` and gives suspects and root
  causes like a written one. A body that calls none adds no claim.
- **With no body and no `uses`**: `f` is taken to call nothing outside
  its own subject. No claim is shown for it. `mitra tie` writes
  `for f::uses fails` when the code plainly calls a function tied to
  another subject, and the claim `f::uses` then exists and fails
  (M002, "the claim itself" against the reader's evidence).
- **What it flags in Mitra's three models: nothing**, once the reader
  stopped guessing. The first run flagged five calls in mitra-core,
  all wrong: `check`, `evaluate` and `plan` "calling
  `report::Logic::as_str`" (it is `String::as_str`), `reader::model`
  "calling `types::read`" (it is the `read` of its own file), and
  `evaluate` "calling `report::word`" (a `let word` of its body). No
  Rust was edited: the default check now only speaks where the text
  settles it (decision 346).
- One golden file gains two lines (`arith::sum3::uses: holds`,
  `arith::between::uses: holds`). 251 tests pass.
- Not done for mitra-ds: `dempster` and `yager` call `is_valid` and
  `conflict` of their own subject, which the default allows and does
  not record. Writing `uses is_valid, conflict` on them would give
  back the single culprit on the `is_valid` break (increment 62); it
  is a change of the model, left to the user.

Decisions taken alone:

345. **The default for a function with no body is the coordinator's
     proposal** ("uses nothing outside its own subject"), not the
     user's words. Alternatives: no default (nothing checked), or
     "uses nothing at all" (every call inside a subject flagged).
346. **The default check only speaks where the text settles it**: a
     method is counted when written `Type::name(…)`, not through a dot
     (`x.name()` may be any type's); a name the calling file defines,
     or the body binds with `let`, is its own. So a call through a dot
     to another subject is not seen. The check of a written or
     body-implied `uses` is unchanged (by name).
347. **The subject of a function is the first part of its name**
     (`mass::Mass::judged` is in `mass`); functions of unnamed blocks
     are one subject.
348. **No claim is shown while nothing is flagged** (unlike `correct`
     and `deterministic`): one more `holds` line per function said
     nothing. Alternative: show `f::uses: holds` for every function.
349. **A body-implied `uses` is `only`**: the spec calls these and no
     other. If the code calls a tied function the spec does not, `tie`
     reports it.

### 65. Helpers and ties as candidates

Asked by the user: "we probably want to have a model to code drift as
possible candidate here"; "yes to adding the candidates on helper and
ties".

- **A helper** (a bare `fn` with a body) read by a failing claim,
  directly or through another helper or a spec body, is a piece of the
  error: `the helper `valid` as written`. It has no code, so it cannot
  drift; it can be the wrong definition. Trusted at 1, or as written:
  `fn valid(m: Mass) -> bool trust 0.8 { … }`.
- **A tie**: where `mitra tie` said a function and its code agree,
  that agreement is a piece of every error on that function: `that
  `s::half` and its code agree (not compared: a is 0..=5 in the model
  and i64 in the code, the numbers of the model computed as the code
  computes)`. It is trusted as the tie's evidence is (`trust n` on
  it). `mitra tie` now writes what it did not compare in the source of
  its evidence: a narrower type of the model, and numbers.
- While nothing doubts them they print under the candidates:

**What `rank` computes today** (the whole trust calculus that runs):

1. Each piece of a conflict has a trust: none, 0, 1, or in between. A
   clause is a set of pieces that can't all be right.
2. Pieces trusted at 1 are taken as right; pieces at 0 or with no trust
   are taken as wrong. For the others, every way of calling each right
   or wrong is listed, weighted by the product of `b` (right) or `1 - b`
   (wrong). Ways where all the pieces of some clause are right are
   dropped; their weight is the conflict.
3. Over what is left: the plausibility that a piece is wrong is the share
   of the weight where it is wrong; the belief is the share where it is
   wrong and it is the only wrong piece of some clause. If the pieces
   trusted at 1 can't all be right, they are opened too and only the
   ways with the fewest of them wrong count.

### 70. Keeping the ledger; the build file; build, conform, assess, diagnose

The rest of the queue: items 1 and 2. Everything here was approved in
outline only, so every detail below is a choice to review.

**Fingerprints** (`crates/mitra-lang/src/fingerprint.rs`). Twelve hex
digits per piece, from what the piece says: comments, spacing and the
order of the declarations do not change it. Used by the ledger and by
the build file.

**The ledger is kept, not only grown** (`docs/reference/ledger.md`).

- `mitra ingest` takes out every `test:` entry and writes the results
  of the reports it is given; `mitra tie` does the same with `reader:`.
  Both say what they replaced and list what was not observed again.
- `mitra add` writes `seen "<fingerprint>"` into what a person says.
  When the piece says something else the entry is stale (`M108`); when
  the piece is gone it is orphaned (`M107`). Either way it stays in the
  file, shows in every report and judges nothing.
- `mitra remove --orphaned | --stale [piece] | --source who | piece`
  takes entries out and prints each one.

**The build file** (`crates/mitra-lang/src/build.rs`, written by
mitra-store under `.mitra/build/`): `model.lock` (every piece, written
or implied, with its kind, fingerprint and what it rests on),
`interface.mitra` (what the code must meet), `owed.txt`.

**The four levels** (`docs/reference/levels.md`): `mitra build`,
`conform`, `assess`, `diagnose`, each running the ones before it and
stopping at the first that fails.

### 71. Contracts

The user asked for it ("Yes let's queue it"), with `contract` as the
word. Proposal: `docs/design/contracts.md`. Reference:
`docs/reference/kw-contracts.md`, three entries with models that run.

**What is in.**

- `contract Name { … }`, outside any block: `fn` signatures, `ensure`
  lines, claims. `Model.blocks` gains the side `Contract`.
- `impl Contract for Type { … }` in a subject or a boundary. The type
  is given each function, promise and claim of the contract. Its braces
  hold only `claim` or `assume` lines.
- `x: impl Contract` as the type of an input.
- A promise of a contract rests on the same promise of each
  implementer; `require need = Contract::promise;` names it.
- M106 also for a block that states intent, takes an `impl Contract`
  and requires no promise of it.
- `mitra build` lists what each implementer owes; the lock names the
  functions of a contract with the kind `contract`.
- The Rust tie needed nothing new: a method in `impl Trait for Type` is
  tied by its comment, and `impl Trait` in the code fits (test
  `tie_compares_an_implementer_with_its_impl`).

**How it is read.** Before anything else, the reader rewrites the
tokens (`parse.rs`, `contracts`): a contract becomes a block of the
world named after it, with `self` any value; an `impl C for T` becomes
an `impl T { … }` holding the contract's signatures, promises and
claims, written in a group of its own after its block; `impl C` as a
type becomes `Any`. The rest of the reader is as before, plus the link
from a contract's promise to its implementers'.

**Decisions taken alone.**

400. A contract is written outside any block and has a name. It is a
     third side, neither subject nor boundary. Alternative: allow it
     inside a block, as `subject::Contract`.
401. A contract holds signatures, `ensure` lines and claims. A function
     with a body is refused (no default method). No associated types,
     no trait objects, no blanket impls.
402. A claim written in a contract is copied to each implementer: a
     claim owed in a subject, an assumption in a boundary. The contract
     keeps no claim of its own. Alternative: contracts hold promises
     only, and each implementer writes its claims.
403. Each implementer is a group of its own, like a block written
     twice: its promises rest on the contract's claims and on what its
     braces say, not on the claims of the block around it, and the
     block's promises do not rest on the implementer's lines.
404. The braces of `impl C for T` hold only `claim` or `assume`. A
     function of its own goes in `impl T { … }`.
405. The promise of a contract rests on the same promise of every
     implementer in the store, and has no capture of its own. With no
     implementer it is assumed on its own word, as a promise of a
     boundary. Alternative: unverified until someone fills it.
406. No verdict per implementer on the user of a contract: one verdict,
     which lists the implementers' pieces it assumes. When one
     implementer fails, the contract's promise fails and names it, and
     so does everything that requires it. Alternative: one verdict per
     implementer on each user, which multiplies the report.
407. An observation names its implementer by the implementer's own
     function (`for radio::Ble::send given …`). An observation on a
     function that takes `impl Link` cannot say which link it had.
408. `impl Link` is `Any` in the type system: nothing new in it. The
     interface `mitra build` writes prints `Any`, and a value that
     fills no contract is not refused.
409. A spec cannot call a function of a contract, as it cannot call a
     function of a boundary: the function says `uses Link::send`. In a
     claim, `l.send(x)` on such a value is `Link::send(l, x)`.
     Alternative: allow the call where every implementer is a subject,
     which makes a spec depend on who fills the contract.
410. The Rust tie is per method. The trait is not tied, and nothing
     checks that the Rust `impl` is of that trait. Alternative: a tie
     comment above the `impl` line, compared with the contract.
411. A contract and its implementers are in one store: `import` does
     not bring a contract from another store or from a module file.
     The files of one store are one text, so a contract in one file is
     filled in another.
412. M106 is reused for the `impl Contract` case instead of a new
     code. `mitra explain M106` still speaks of `uses` only.
413. Mitra's own model gained `contracts.mitra` (what a contract is)
     but uses no contract: the natural case, the reader role mitra-rust
     fills and the CLI names, is across two stores (411).

**What to review.** `docs/reference/kw-contracts.md` first. Then
decisions 402, 405, 406 and 409: they are the ones a first model will
meet. `crates/mitra-lang/.mitra/contracts.mitra` for Mitra's own words.

### 72. Generics, with a contract as a bound

The user asked: "Can you take Rust grammar and semantic on generic?
With a possible contract constraint on the type?" Proposal:
`docs/design/generics.md`. Reference: `docs/reference/kw-generics.md`.

**What was there.** `fn f<T>(x: T) -> T`, `record Pair<A, B>` and
`enum Tree<T>` were read, each parameter as `Any`. Refused: a bound,
`where`, `impl<T>`, a parameter on a contract.

**What is in.**

- Bounds: `fn push<L: Link>(l: L)`, `<L: A + B>`, `where L: Link`.
  `l: impl Link` is the same with no name. `Model.bounds` keeps, per
  function, each input and the contracts that bound it.
- `impl<T> R<T> { … }`, `impl R<Int> { … }`, a bound on the `impl`.
- `contract Store<K, V> { … }`, `impl Store<Int, String> for Cache`,
  `impl<T> Store<Int, T> for Shelf<T>`.
- A bound leans on its contract as `impl Contract` does: a `require` on
  a promise of it is expected, M106 otherwise.
- `mitra tie` compares the bounds of each bound input with the traits
  in the code (`<L: Link>`, `where`, the `impl` line, `impl Link`,
  `&dyn Link`), and a `record R<T>` with its `struct`, which it refused
  before ("the code is a struct, not an enum").
- The interface `mitra build` writes prints type parameters, bounds
  and `impl Contract` as written, and `record R<T> { … }`.

**Against the coordinator's reading.** Grammar: all the forms listed
are read. Meaning: two differences, both flagged below (414, 416).

**Decisions taken alone.**

414. A type parameter is `Any`, bound or not. Rust's rule, that a body
     may use of `T` only what its bounds promise and that an unbound
     `T` is opaque, is NOT enforced: `x + 1` on an `x: T` is read.
     Enforcing it needs an opaque type in the type system. What a bound
     does: it is recorded, it makes the block lean on the contract
     (M106), and the tie compares it.
415. A bound names contracts and nothing else. `T: Clone` or `T: Ord`
     is refused ("`Clone` is not a contract"). Alternative: let unknown
     bounds through unread, which hides typos.
416. `f::parametric` is not built. Evidence at an instance is a point,
     as any pinned output. Every input type that holds a parameter is
     infinite (`Any`), so no finite evidence covers it with or without
     such an assumption: the piece would change no verdict today.
417. The instance is chosen at the call and never written: no
     `f::<Int>(x)`.
418. `impl<T> R<T>` gives each function the parameters of the `impl`
     before its own (`fn zip<T, U>`). In a claim of such an `impl`, `T`
     is written `Any`: claims take no type parameter.
419. A contract's parameters become parameters of each of its
     functions. An implementer must give as many types as the contract
     has parameters; they are substituted in what it is given.
420. In a bound, the types given to a contract (`S: Store<Int, String>`)
     are read and not used: the bound is the contract's name. Two
     bounds on two instances of one contract are one bound.
421. The tie matches a trait to a contract by its last name
     (`crate::net::Link` is `Link`), checks only the inputs the model
     binds, and lets the code bound them by more (`L: Link + Clone`).
     A parameter that is not the whole type of an input (`xs: List<T>`
     with `T: C`) is not compared.
422. No bound on a `record` or an `enum`; no parameter on a `subject`
     or a `boundary`.
423. The interface prints a function with parameters as its tokens
     were written (`fn pull<L>(l: &L) -> List<Int> where L: Link;`),
     set tidily; an implementer's copy of a contract's function loses
     `impl Contract` on its inputs and prints `Any`.
424. `mitra tie` no longer lists the functions of a contract under "no
     code is tied to", and now lists a `record R<T>` that has no tie.

**What the dogfooding found.** A `record R<T>` could not be tied to its
`struct` at all before this increment: the reader holds it as an enum
of one variant and the tie compared it with an enum.

**What to review.** `docs/reference/kw-generics.md`. Then 414 first:
it is where this departs from "Rust's semantics". Then 415 and 416.

## Increment 86: a test owes passing and correctness (2026-11-20)

**Asked.** "the claim holding is directly your belief of the test
correctness. The test passing without review gives you the base bias
on test evidence. The test review gives you a judged opinion on its
correctness… Once you get that test passing and correctness reviewed
at 1, the verdict on claim should be hold. The verdict on claim
without review, should be hold or unverified, based on the bias
baseline… Bias is a per evidence confidence baseline, policy is a
threshold of holding on a claim." "make this simple exemple work, and
tested with a golden model test set in Mitra." Then: "the author of
the evidence is giving his opinion on how certain he is, and that is
the bias of the review evidence."

**What changed.**

- Settings: `[bias] test = 0.5` and `[policy] holds = 0.9`.
- With a bias, a verdict that stands on tests carries a confidence
  (`verdicts/confidence.rs`, a step after each verdict): an
  unreviewed test at the bias, a reviewed one at its review's `trust`,
  the product over the tests a verdict needs and over the claims it
  follows from. Under the threshold a claim reads `unverified`, and
  what follows from it sees that.
- The report: a line `confidence`, a line `on` per test, a line
  `from` for what it follows from. `mitra next` and the warning list
  the reviews owed, each with the evidence line to write.
- The golden set, `examples/trust/`, thirteen cases with their reports (seven at first),
  run by `crates/mitra-lang/tests/trust.rs`: passing only (unverified
  at 0.5), reviewed at 1 (holds), reviewed at 0.8 (unverified),
  failing (fails), a threshold of 0.4 (holds at 0.5), derived from
  two points (1 and 0.5, the promise 0.5), no bias (as before).

**Decisions taken alone.**

533. Off unless `[bias]` is in the settings: Mitra's stores, the
     rungs and every other report are unchanged. To turn on for all
     once the rest of the trust system is settled.
534. Wording, least committal: the verdict words stay, and the number
     is a line `confidence` under them. No `holds assuming n`, no
     `follows`.
535. Below the threshold the word is `unverified` (your "hold or
     unverified, based on the bias baseline"): reading A of trust.md.
536. A failing test reads `fails` whatever the threshold, with its
     confidence under it. The alternative, a failure below the
     threshold reading `unverified`, would hide failing tests.
537. Combination is a product, and where two ways reach the same
     inputs the better one counts. No fusion of independent opinions:
     subjective logic proper is not coded.
538. A review's certainty is its `trust`, taken as written with no
     cap and no weight for who the reviewer is. The `doubt` of voices
     still prints beside it and is a second, unrelated number.
539. Only tests are weighed. A review of a claim or of a capture, a
     sample, a tie count as before, as if believed at 1.
540. Mitra's own model does not say this step yet.

**More cases, asked after** ("what a contradictory review does, what
not passing against correct review does, what passing against not
correct review. How confidence of review influence the holding and
bias of the test… a two claim with a single point test disagreing").
Six more goldens, 13 in all:

| Case | Mitra says | Reads right |
|---|---|---|
| 9 failing, reviewed correct at 1 | `fails`, confidence 1 | yes |
| 10 passing, reviewed as wrong | `unverified`, confidence 0 | yes |
| 12, 11, 3, 2: reviewed at 0.3, 0.5, 0.8, 1 | 0.3, 0.5, 0.8 unverified; 1 holds | yes: the review replaces the bias, down as well as up |
| 8 two reviews that disagree | `holds`, confidence 1: the better review wins | **no** |
| 13 two claims that disagree | `next::deterministic: fails`; the code is the only suspect, `certain` | **no** |

What 8 asks of the trust system: two opinions on one test must be
combined, not picked from; at 1 against 1 the test is in conflict and
should be an error naming both reviews. What 13 asks: a disagreement
between two claims is first a wrong claim or a wrong test, and the
suspects are the two claims and the two tests, weighed by how far

unreviewed test first). Both goldens are kept as Mitra says today,
and their tests are named `…_not_weighed_yet` and `…_not_ranked_yet`.

**Known limits.** A claim tested directly and also derivable from
reviewed points is right (the better way counts). A claim computed
from several observed outputs lists every evidence line it read as
needed, including one that only repeats another: it can come out
lower than it should, never higher.
